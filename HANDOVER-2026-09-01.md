## What Was Built

### Core Schema Layer
- **`mwgym/schema/world.py`** — `WorldGenome`, `FailureVector`, `GateResult`, `CapabilityScore`
  - WorldGenome: immutable world configuration (family, difficulty, structure, information, resources, perturbations)
  - FailureVector: what went wrong in a run (gates, capabilities, failure modes, economics)
  - CapabilityScore: per-capability score with running stats

### CGE Adversarial World System
- **`mwgym/worlds/schema.py`** — `FamilyWorldSpec` + 11 registered Oracle task families
  - software.implementation, software.maintenance, research.analysis, research.verification, ideation.technical, content.writing, support.customer_service, data.processing, business.decision, venue.autonomy, compute.routing
- **`mwgym/worlds/cge_adapter.py`** — Compiles WorldGenome → executable CG worlds
  - Implements: reset(), observe(), actions(), apply(), terminal(), score()
  - Three concrete worlds: SoftwareBugFixWorld, ResearchVerificationWorld, ComputeRoutingWorld
  - `to_failure_vector()` produces FailureVector from completed world state
- **`mwgym/worlds/adversary.py`** — Failure-guided WorldGenome mutation
  - 7 mutation strategies: staleness_increase, conflict_injection, distractor_growth, budget_squeeze, step_pressure, debug_challenge, novelty_injection
  - MAP-Elites archive for niche-based world retention
  - Teacher objective: frontier × regret × realism × novelty
- **`mwgym/worlds/curriculum.py`** — MAP-Elites curriculum selection
  - Replay best worlds + explore underserved niches
  - Scores worlds for specific worker based on weakness targeting

### Unified Hydra DB
- **`mwgym/hydra_unified.py`** — Single SQLite store for ALL MWGym data
  - Tables: runs, world_genomes, worker_genomes, capability_evidence, failure_modes, curriculum_archive, experiments, insights, graph_nodes, graph_edges
  - Methods: record_run(), record_world_genome(), record_capability(), record_failure_mode(), family_stats(), worker_vs_worker()
  - Indexes on family, worker, world, experiment

### PydanticBATS Harness
- **`mwgym/harnesses/pydantic_bats.py`** — PydanticAI-style harness with BATS routing
  - UsageLimits: request_limit, cost_limit_usd, token_limit, tool_call_limit, wall_time_limit
  - UsageTracker: enforces limits before every request
  - BATSRouter: selects model based on task, budget, uncertainty, Hydra posterior
  - Models: mimo-v2.5 (free), llama-3.3-70b-versatile (cheap), llama-3.1-8b-instant (cheap)
  - Single model call → ActionBundle → apply writes → git commit
  - Produces HarnessRun + FailureVector

### Git Workspace
- **`mwgym/workspace.py`** — One lab repo + worktrees per run
  - `LabWorkspace`: creates/manages `/root/mwgym/lab/`
  - `RunWorktree`: per-run worktree with branch `mw/run/{run_id}`
  - Pattern: init → seed world (B0) → worker output (B1)
  - NOT separate repos per run (wrong pattern, now fixed)

### LabBrief
- **`mwgym/lab_brief.py`** — Empirical memory for workers
  - Queries Hydra for prior runs on a family
  - Returns: stats, model economics, capability evidence, failure patterns, recommendations
  - Worker receives this BEFORE execution
  - Brief itself is recorded as input artifact

### Wired Loop
- **`mwgym/wired_loop.py`** — The real production loop
  - Steps: Git worktree → LabBrief → World compile → BATS route → Execute → Git commit → Hydra record → FailureVector → Adversary → Report
  - Supports: pydantic-bats, letta harnesses
  - Records: runs, capabilities, failure modes, graph nodes/edges, world genome stats

### Datasets
- **`mwgym/datasets/submissions-v1/`** — 5 real coding tasks
  - task-001-rate-limiter, task-002-json-diff, task-003-lru-cache, task-004-markdown-table, task-005-config-merge

## The Hybrid Architecture (from letta-aligned.md)

```
Letta (persistent brain)
    │
    ├── PLAN: interprets task + experience
    │
    └── mw_delegate(TaskSpec)
            │
            ▼
    Moltwork Executor
    ┌─────────┼──────────┐
    ▼         ▼          ▼
  direct   Pydantic   stateless
   LLM       agent      Letta
```

Key principles:
- Letta = strategic cognition (planning, synthesis, learning)
- Pydantic = cheap execution (request_limit=1, cost tracking)
- Git = durable substrate (worktrees, MemFS, skills)
- Hydra = empirical memory (what worked, what failed)
- CGE = adversarial curriculum (evolving worlds)

## The 21-Step Production Loop

1. ORACLE → pick opportunity/family
2. MWGYM → choose task or CGE world
3. GIT → fresh worktree, commit B0
4. FREEZE → WorkerVersion, WorldVersion, ComputePolicy
5. HYDRA → retrieve LabBrief
6. LETTA → persistent agent, fresh session
7. PLAN → Letta interprets task + experience
8. ALLOCATE → ComputeBroker routes
9. EXECUTE → free/cheap workers under BATS
10. SYNTHESIZE → Letta reviews results
11. GIT → commit B1
12. VERIFY → deterministic verifier
13. WORKERKIT → record artifacts, costs, outcome
14. HYDRA → project empirical result
15. REFLECT → trajectories + FailureVector
16. PROPOSE → memory/skill candidates
17. GIT WORKTREE → apply candidates
18. MWGYM → incumbent vs candidate
19. CGE1 → shrinkage + replace-if-wins
20. PROMOTE → merge or reject
21. REPEAT
